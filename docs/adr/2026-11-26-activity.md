# Activity: time per repository and branch, for timesheets

- **Status:** accepted, built 2026-11-26 and 2026-11-27 on `feat/activity`, used by the user for their timesheets from 2026-11-26 (the
  gaps and the estimate are still to be adjusted from use).
- **Decided:** with the user, 2026-11-26 and 2026-11-27.
- **Came from:** `docs/plan-activity.md` (never committed), retired into this record on 2026-11-27: its want is the context below, its
  WakaTime notes are at the end, and what it left open is under "Not built".

## Context

The user fills in a timesheet once a day and needs the day's time split per **repository and branch**, with a few lines on what was done
in each. Per folder is no use: they keep several checkouts of one repository (`yumbi`, `yumbi.alt`, …), switch branches inside them, and
pick up a pull request's branch in whichever checkout is free. WakaTime gives time per project only (two branches of yumbi-web, a small
fix for a review comment on one and most of the day on the other, can't be told apart); their own `show-commits-for-today` gives each
folder's branch and the day's commits, but no time. They extrapolate to a day by hand and add meetings and standup, which vibe needn't
do: **the ratios are what matter.**

WakaTime itself was looked into first and set aside: its per-branch figures need an API key, and sending the agent's time would need
that key inside the sandbox (notes at the end).

## Decision

**An Activity tab**, on every page (the Profiles page too), covering every folder vibe has opened: the sandboxes vibe has records of, and
every folder in the activity log, so a day still shows after its sandbox is deleted. No other folder is looked at.

**Evidence**, each a mark of "work on repository R, branch B, at time T":

- **Vibe's own log**, written on the host while a sandbox's page runs: `~/.vibe/activity/<YYYY-MM-DD>/<sandbox>.jsonl`, a JSON line
  `{at, folder, repo, branch, kind, text}` each, one file per sandbox so two companions never write to one. Kinds: a prompt sent (the
  conversation, a review's Ask or Submit), the agent working (each minute **while a turn runs**: tasks left running after it cost
  nothing, and aren't marked), the user on the page (keys, clicks, wheel; said at most once a minute), a review action, and the folder's
  git status changing (seen by the page's polls). At most one mark of a kind on a branch a minute, but every prompt the user sends
  from the page is marked, with its start (`text`: its first 200 characters, on one line) for the summaries; a review's prompts are
  vibe's, and are marked without. The repository is named from origin
  (`activity.RepoName`), read every five minutes.
- **Git, after the fact:** HEAD's reflog is the timeline: its checkouts say which branch HEAD was on, and what was committed, merged,
  cherry-picked or rebased then is that branch's. Deleting a branch deletes its own reflog, but not HEAD's record of the work done on
  it: a branch merged and deleted the same day still shows (found 2026-11-27, when a morning's work on a deleted branch was missing).
  Each branch's reflog adds only the moves HEAD's didn't record (a branch moved while HEAD was elsewhere), so nothing counts twice. Read **with go-git in the review helper** (`review.History`), never with git: the sandbox can write the folder's
  `.git/config`, and git would run what it names on the host. Reflogs are read from their end, at most 4 MB each.

**From marks to time** (`activity.Summarise`, pure, table-tested):

- A mark stands for the minute after it; marks on a branch no more than 15 minutes apart join into one **measured** stretch.
- Git's events on a branch no more than an hour apart count in full; the first piece of work in a run counts 15 minutes before it.
  **Estimated.** A checkout, pull or reset is a **link**, no work of itself: it joins work either side of it and starts the work that
  follows it (from the checkout, when that's more than 15 minutes before), but a run of links alone counts for nothing, and the
  stretch ends at the last piece of work, not a later link (2026-11-27: switching to master and pulling it counted half an hour).
- Measured time covers estimated time on the same branch: it counts once, as measured. Branches worked on at once each count in full.
- The day is local midnight to midnight; a stretch is cut there.
- **The day's total is rounded to the nearest step** (15 minutes, half an hour, an hour; exactly half going up) **and shared out**
  between its branches in whole steps: each gets its whole steps, and the steps left go to those with the most left over (the
  longer first where that's even), the largest-remainder method. So no branch is more than a step off its time, and the parts add
  up to the rounded whole: four 10-minute fixes at half-hour steps keep their half hour, on the longest. One setting for all of
  vibe: `activityRounding` in `~/.vibe/settings.yaml`, half an hour unset.
  - **Changed 2026-11-27, with the user, after a day of use.** It was rounded **up**, with any work at least one step (the cost of
    switching to it): a 30-minute step made 30 minutes 5 seconds of switching to master to pull an hour, and 33 minutes an hour. The
    step is now what the user's timesheet counts in. Rounding each branch to its nearest step was tried first, and replaced the
    same day by sharing out the day's total: on its own, it loses small tasks (each rounding to nothing) and their sum with them.

**Bullets** (`activity.FromHistory`): the first line of each commit by the user (author email as `user.email` says in the repository,
else the user's git config; every commit when there's none) **authored** that day, so a rebase doesn't bring last week's commits into
today. A rebase is one event and one bullet, "rebased onto master" (`origin/` dropped); a merge, "merged master" (a fast-forward
too); a pull is an event and no bullet; an amended commit replaces its bullet. A merged branch is named plainly ("merged
master" for `refs/remotes/origin/master`, `refs/heads/master` and `origin/master`); another remote's prefix is kept, as it can't be told
from a branch's own folder (`feat/x`). The same text on a branch is one bullet.

**The page** (laid out with the user 2026-11-27, after a day's use; the day's controls after Harvest's): `←`, the date, `→` in one
group, the date opening a list of the days kept (Today, Yesterday, then by name: a month calendar would be mostly days that can't
be chosen; eight days at first, fourteen since 2026-11-27, see The week), and a **Return to today** link shown only on another day. The help is in a balloon from an (i) beside the step buttons,
closed by the (i), Escape or a click elsewhere. **Branches are grouped by repository** (2026-11-27): a heading with the repository's
total (its branches' hours, which add up as the day's are shared out) and share of the day, always open (it doesn't look like a row
that opens, so isn't one), its branches' rows indented under it; repositories and branches in order of time, the longest first, then by
name, so equal times hold still. Every bar is a share of the day. The columns right of the name are fixed widths, so a heading lines up
with its indented rows; too narrow for a bar, there is none. Each branch is a row of branch, decimal hours, a meter of its share of the
day, "~estimated" if any of it is, and a mark while its summary is being made or when it failed. **Rows start closed, and one is open
at a time**: opening one closes the other, keeping the row clicked where it was on the screen (closing one above it would pull it from
under the pointer). A row's own (i) shows its stretches, the time before rounding and its folders. A branch with no time once rounded
and no commits or prompts is hidden behind "N hidden: show" (a long investigation without commits shows by its time). An open row shows,
side by side (one over the other when narrow), its **Summary** and its **Commits** (or, for a branch with none, what was **Asked**)
(`:bug:`-style codes drawn as emoji), each with its own copy button, which copies `- line` bullets as shown, emoji and all: the user
logs time per branch, against the card it belongs to, so a day-wide Copy was taken out. Nothing is edited on the page: it shows, and
the user edits what they paste. The tab asks again every 15 seconds while open (each folder's git is read at most once
a minute, its status every 15 seconds), and redraws only on change, so an opened row stays open and focus stays put. What can't be read
(a folder's git, a cut-short log line) is listed, not hidden.

**Needs attention** is git's state **now**, so it shows on today only (and, since 2026-11-27, in a week that has today in it): uncommitted changes, "N commits not pushed", "never pushed" (no
upstream). It is a "⚠ N" button in the bar, not a card above the day (2026-11-27): the same few reminders sat over the rows all day,
and the user didn't want an ignore list (an ignored folder is forgotten). Its balloon pops up of itself only when the list changed
since it was last seen (what was seen is kept in the page's localStorage, so a reload doesn't pop it up again), once GitHub has
answered, and closes itself after 6 seconds, a bar counting down; the pointer or focus on it holds it open. Opened from the button, it
stays until closed (the button, Escape, a click elsewhere), as the status balloon does. Before saying commits aren't pushed, GitHub is asked in the background (the host's gh, in a folder of its own, for the
branch's head: `ghRemoteHead`): a branch pushed by URL, whose local copy of the remote is stale, is then left out, and a count is from
GitHub's head when the folder has it. "Checking with GitHub…" shows meanwhile; without gh, the local count stands.

## Summaries of the commits (decided with the user 2026-11-26, after trying the tab)

**Context:** for a timesheet entry the user writes 1 to 3 lines that give the gist of a branch's day, not its commits.

- **Made without being asked:** whenever the tab shows a day with branches whose commits haven't been summarised (the first look, new
  commits since, or the rules changed), they are summarised in the background, all of that day's at once, in **one** ask. "Summarising…"
  shows meanwhile, and the tab asks again every 3 seconds until it's done.
- **A branch with no commits is summarised from its prompts** (2026-11-27): a day of planning or investigating left nothing to
  summarise. The starts of the day's prompts on the branch are given instead (oldest first, once each), with an instruction to say what
  the work was, not what was asked, and not that there were no commits (the first one echoed "(planning, no commits)"). A branch with commits is summarised from them alone: they tell its day, and prompts would add
  noise. Only prompts sent from vibe's page are known; the user accepted their starts going to another project's sandbox, as commit
  subjects do. The instruction is in the fixed part of the ask, not the user's rules, so rules already written get it too.
- **By a one-shot Claude in the sandbox of the page being looked at** (`claude -p --tools "" --strict-mcp-config --no-session-persistence --model haiku`, in `/tmp`, as the
  instructions' Optimise does): not the conversation's agent, whose context it would fill. Any sandbox's page can do it: none is
  special, so the page left open at the end of the day is enough. The sandbox is started if it is stopped, as the page does anyway.
  - **Marked as vibe's own** (2026-11-27): a summary's session ran the clipboard hook as any prompt does, and took a screenshot the user
    had just pasted for their next message, marking it sent; the message went without it. Every claude vibe runs for its own ends (a
    summary, the instructions' Optimise, the model list) now runs with `VIBE_CLIPBOARD_HOOK=off`, and the hook leaves the paste for the
    user's prompt. The hook's side is in the library, so it reaches a sandbox once its profile is re-composed.
  - **No tools at all** (2026-11-27): `--tools ""` left the MCP gateway's tools, and the summary's session tried to call one;
    `--strict-mcp-config`, with no config given, takes them too (both seen in the sessions' transcripts). It matters here: a summary is
    given other repositories' commit subjects.
  - **No session kept** (2026-11-27): `--no-session-persistence`, so the ask leaves no transcript in the sandbox, where the agent's
    memories or a later `--resume` could pick up other projects' commits and prompts.
- **Across every folder vibe has opened**, as the rest of the tab: commit subjects of one repository go to another's sandbox. The user
  chose this over starting each folder's sandbox (work in NExpect or PeanutButter for yumbi is yumbi's time, and seen together), and
  over asking first. Only subjects (or prompts' starts), repository and branch names, and the rules are sent: never diffs. The subjects are given as quoted
  JSON data, and the agent has no tools; what it says is shown as text.
- **Kept on the host, shared by every vibe:** `~/.vibe/activity/summaries/<key>.json`, the key a hash of the day, repository, branch,
  commits (or prompts), rules and the ask's own fixed wording, so a summary is made once and only made again when one of those
  changes.
- **One vibe summarises at a time:** an OS lock on `~/.vibe/activity/summaries/summarising.lock` (`internal/filelock`), with the
  holder's sandbox name written in it; another vibe's page says "Activity is being summarised on the yumbi vibe, and will appear here
  shortly". The system lets go of the lock when that vibe ends, however it ends, so none is ever left stale (this replaced a lock file
  refreshed every few seconds, discussed first).
- **Rules the user can edit:** `~/.vibe/activity/summary-rules.md`, written from the default (`internal/activity/summary-rules.md`) the
  first time: 1 to 3 bullets; related fixes grouped; ADRs, docs and refactoring are "prepare PR for review"; fixes from review are
  "responded to PR commentary"; no emoji or code names. Changing them summarises again.
- **A failure** (signed out, no sandbox, an answer that isn't the JSON asked for) is kept and shown with its reason and **Retry**; it is
  not tried again by itself, so a signed-out agent isn't asked at every look.
- **Claude only:** no tester, no feature. Another agent's page shows the commits, and "Commit summaries are only shown for Claude
  agents. If you'd like codex to be supported, please ask for it with Request a feature, in the power menu." The Profiles page has no
  sandbox: it shows summaries other pages made, and says to open a sandbox's Activity tab for the rest.
- **Not done:** telling "responded to PR commentary" from the pull request's reviews (which commits came after one) rather than guessing it
  from the subjects; later, if guessing isn't good enough.

## Ticket links and copying a branch's summary (decided with the user 2026-11-27)

**Context:** the user's time entries start with the ticket's link (a Trello card, as Harvest's Trello plugin did), then the summary.

- **A copy button on each branch's row** (and the open row's Summary copies the same): the ticket link, when set, on the first line,
  then the summary's bullets; no hours (a timesheet has a field of its own). It is disabled until the summary is ready.
- **"Ticket link"**, worded for any tracker, set in the row's (i) balloon; only an http(s) address is kept (the row links to it, opening
  in a tab of its own, `rel="noopener noreferrer"`). It never goes to the summariser: only into what is copied.
- **Kept on the host by repository and branch** (`~/.vibe/activity/tickets.json`), so every checkout of the repository, and every vibe,
  has it.
- **Forgotten on positive evidence only**, as the week is read: every checkout vibe knows could be read, the repository has at least one,
  the branch is in none of them nor among origin's branches as last fetched, and neither the log nor git mentions it in the days kept
  (a week until 2026-11-27, fourteen since). A stalled branch keeps its link; so does a deleted one worked on in those days. A
  branch's name is more often reused months apart than within a fortnight, and what was copied before then is the user's already.
- **Not built:** offering a link from the branch's pull request (its description), and giving the link to the agent for its pull
  request descriptions: a round of their own, once links are in use.

## The week (decided with the user 2026-11-27)

**Context:** the user wanted to see how the week split between projects at a glance, and each day's breakdown too. Compared in a
throw-away page (`tmp/week-compare.html`): a pie, ranked bars, and a column per day stacked by repository. The ranked bars compare
more exactly, but the user found the pie's relative sizes (one big project, two middling, many small) read faster, and wanted the
daily shape as well: both are shown.

- **Day | Week** in the bar (kept for the page). In Week, ← and → step a week, the date lists the weeks kept, and Return to this week
  comes back. Weeks run **Monday to Sunday**; days before the first kept are said ("Mon, Tue are before the days kept").
- **The days kept became fourteen** (`HistoryDays` = `KeepDays` − 1, so today and thirteen before): with seven, last week was missing
  its first days all this week. Each folder's git is read that much further back.
- **A repository's week is the sum of its days' rounded hours**, as each day rounds them, so the week adds up to what was logged day
  by day (`Desk.Week`, which reads the log and git once for the week and summarises each day as `Day` does). A branch with commits or
  prompts stays in the week though its time rounds to nothing, as on a day: listed at 0% with its commits, and no slice (found in
  review, 2026-11-27: such a branch, and its work, had dropped out of the week).
- **The pie** (largest first from 12 o'clock) **beside its list** (hours and share; the list carries the figures, as a pie can't)
  **beside a column per day**, stacked by repository (the week's largest at the bottom), its total on top. Picking a repository in
  either chart or the list dims the rest and shows its branches below, laid out as the day's rows are, with their week and each
  day's hours. The slices and the list are reached by Tab, moved between with the arrow keys, picked with Enter; hovering says each
  day's hours.
- **Fills, not just colours.** The user has fourteen repositories in use, more than colours that stay apart. Checked with the
  dataviz palette validator, every pair against every other (a repository keeps its fill, so any two can meet):
  - **Normal:** 9 colours, every pair at least ΔE 15 apart for normal colour vision and at least 3:1 against the panel, in both
    themes, each repository the same hue in each; chosen for saturation (the user found the first, duller set washed out). Then each
    colour again striped /, dotted, striped \ and cross-hatched, a colour's repeats each with a different pattern: 45 fills before
    "Other" (grey).
  - **Colour-blind-friendly** (a checkbox under the columns, kept as `activityColourBlind` in `~/.vibe/settings.yaml`, for every page):
    the 3 hues that stay apart for colour-blind readers, each solid, striped /, striped \, dotted and cross-hatched: 15 fills, told
    apart by pattern when not by hue. No browser or system says a reader is colour-blind, so it is a choice; it is on by itself in the
    system's high contrast (`forced-colors`), whose colours replace the page's. Not in the power menu: the theme there is the
    sandbox agent's, not the page's.
  - Patterns are the panel's colour over the fill's (lines or dots), so they read in both themes; they need about 8px, so the
    thinnest slices show colour alone, and the list, hover and picking say which is which.
- **A week's summary per branch** (decided with the user 2026-11-27): for the end-of-week meeting, with people who aren't at
  standup, the user re-tells what happened on each branch. A branch's row opens (several may be open; they start closed) to its
  **week's summary**, up to 10 bullets of up to 600 characters (a day's: 300; a week's bug-fix line names many), the most important first, beside its **Commits** by day ("Thu · fixed the pie"), or what was
  **Asked** for a branch with none. Made as a day's summaries are (the same store, lock, Retry and one ask for all the week's
  branches, kept by the week's commits, rules and ask), under rules of its own, `~/.vibe/activity/week-summary-rules.md`, as the
  day's ask 1 to 3 bullets. A row's copy button copies it, the ticket link first. No summary per repository, as on a day.
- **The rules are edited on the Admin tab** (decided with the user 2026-11-27): an "Activity summaries" card, beside the agent's
  instructions, with the day's and the week's rules, each with Save and "Back to the default" (which only fills the box). They are
  vibe's, not the sandbox's, and rarely changed, so not on the Activity tab, whose (i) links to the card. A save is refused when the
  file changed since it was loaded (by hand, or on another page), with Reload, rather than merged: they are short, and the user's.
- **One button opens every row, unless all are open, when it closes them all** ("Expand all" / "Collapse all"). The user first
  asked for the other way round (any open: Collapse all); this way, opening one row to look and then wanting them all is one
  click, not two.
- **A repository keeps its fill** (`~/.vibe/activity/fills.json`, by number) while it is worked on in the days kept: it gets the lowest
  free number the first time a week it is in is shown (the week's longest first), and is freed once it hasn't been seen since the
  first day kept. So a repository is drawn the same in every week the page can show, and the fills in use are the repositories of a
  fortnight, not all there are. Vibes share the file without a lock: two giving out fills at once give the same repository the
  same one, and a clash between different repositories is put right by the next look. A file that can't be read is begun afresh,
  and the page says so.

## Consequences

- Git marks come only while a page polls; outside vibe, time is git's estimate, from commits and checkouts.
- The log grows by a few kilobytes per sandbox per active day. Fourteen days are kept, today among them: a week past what the page
  steps back to. The first look at the tab each day removes older day folders, and summaries made before the first day kept (by the
  file's time: a summary is keyed by a hash, not a date). Ticket links, the rules and the lock stay.
- A branch with time but no commits and no prompts sent from vibe (worked on outside it) shows no bullets; Needs attention is where
  uncommitted work is warned about.

## Not built

- **Catching edits outside vibe** that never become a commit (a watcher running all day); the estimate stands in for now.
- **Marks from a terminal session** (the agent's own window, not the page's conversation): only the page's prompts and turns are
  marked, so work done there shows only through git. Claude hooks in the sandbox, telling the page of each prompt and turn, were
  designed (they'd need the library, so a re-compose, and Claude only) and put off by the user on 2026-11-27. Reading the agents'
  transcripts instead was set aside: slow through `sbx exec`, only while the sandbox runs, and their format is the agent's.
- **A ticket link offered from the branch's pull request** (its description), and the link given to the agent for its pull request
  descriptions: a round of its own, once links are in use.
- **Tuning the gaps** (the 15-minute join, the hour between git events, the 15 minutes before a run) from use.
- **`vibe --clone`** (`docs/plan-clone.md`) would add checkouts this picks up with nothing extra: they are folders vibe has opened.

## Verified by hand (the user, 2026-11-26 and 2026-11-27)

The tab on real days' work across their repositories; summaries made by a real Claude, a day's and a week's (the week's taking about a
minute); a branch with only prompts summarised from them (NExpect); the clipboard left alone by the summaries; copying a summary with its
ticket link first; Needs attention's button and balloon; the week's charts, picking, Expand all and Collapse all; the rules card, a save,
and a save refused after an edit by hand.

## Not verified

- The summarising lock between two vibes summarising at once.
- The GitHub check on a branch pushed by URL (the local copy of origin stale).
- Pruning on a real fourteen days' log.
- The 15-minute join, the hour gap and the 15 minutes before a run are first guesses, to be adjusted from use.

## WakaTime, looked into and set aside (2026-11-26)

- **Sending:** `wakatime-cli --sync-ai-activity` reads agents' transcripts (Claude's `~/.claude/projects`, and about 60 others) and
  sends "ai coding" heartbeats with AI and human line changes and tokens. The official `claude-code-wakatime` plugin runs it from hooks,
  at most once a minute.
- **Reading:** the CLI's `--today` call (`/users/current/statusbar/today`) gives no branches. Per-branch totals need
  `/users/current/summaries?start=&end=&project=`, unverified, as wakatime.com refuses automated fetches.
- **Auth:** the API key in `~/.wakatime.cfg`, sent as HTTP Basic auth with the key base64-encoded.
